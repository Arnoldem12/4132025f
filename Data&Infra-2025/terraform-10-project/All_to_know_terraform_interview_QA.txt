Q: How do you manage Terraform in teams?
A: Use remote backends (like S3 with DynamoDB lock), break infra into modules, version your state and config in Git.

Q: Difference between count and for_each?
A: count is for indexed resources, for_each is for named items (map or set).

1.What is Terraform and what problem does it solve?
    A: Terraform is an open-source Infrastructure as Code (IaC) tool created by HashiCorp. It allows users to define and provision infrastructure resources using a declarative configuration language called HashiCorp Configuration Language (HCL).
        The main problems Terraform solves are:
        -Infrastructure provisioning across multiple cloud providers with a single consistent workflow
        -Version control for infrastructure
        -Automated deployment that reduces human error
        -Creating reproducible infrastructure
        -Managing complex dependencies between resources

5.What file extensions does Terraform use and what are they for? 
    A: Terraform uses several file extensions:
        .tf - Contains the main Terraform configuration code written in HCL
        .tfvars - Used to define variable values
        .tfstate - Stores the state of the infrastructure
        .tfstate.backup - Backup of the previous state file
        .tf.json - JSON format of Terraform configuration (less common)
        .tfplan - Binary file created when you run terraform plan -out=filename

1.How would you manage Terraform state in a team environment?
    A: In a team environment, I would manage Terraform state by:
    -Using a remote backend like S3 with DynamoDB for state locking to prevent concurrent modifications
    -Setting up proper access controls to the state backend
    -Separating state files by environment or component to limit the blast radius
    -Using workspaces for environment isolation when appropriate
    -Implementing CI/CD pipelines that handle state operations
    -Setting up automated state backups
    -Establishing a process for handling state conflicts
    -Avoiding manual state manipulation except in emergency situations
Example:
terraform {
  backend "s3" {
    bucket         = "company-terraform-state"
    key            = "prod/network/terraform.tfstate"
    region         = "us-west-2"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

6.What's the difference between count and for_each?
    A: Both count and for_each allow you to create multiple instances of a resource, but they work differently:
    -   count creates multiple identical resources based on a number.
        The main drawback is that if you remove an item from the middle of the list, 
        resources get recreated because Terraform identifies them by their index.
                    resource "aws_instance" "server" {
                        count = 3
                        ami   = "ami-0c55b159cbfafe1f0"
                        instance_type = "t2.micro"
                        tags = {
                            Name = "Server-${count.index}"
                        }
                    }
    -  for_each creates resources from a map or set of strings, 
        identifying resources by unique keys. This avoids the reordering problem of count.
                    resource "aws_instance" "server" {
                        for_each = {
                            web = "t2.micro"
                            app = "t2.small"
                            db  = "t2.medium"
                        }
                        ami           = "ami-0c55b159cbfafe1f0"
                        instance_type = each.value
                        tags = {
                            Name = "Server-${each.key}"
                        }
                    }

3.How would you organize Terraform code for multiple environments (dev, staging, prod)?
    A: There are several approaches I've used for organizing Terraform code across environments:

        -Directory Structure Approach: This provides clear separation but can lead to code duplication.
            a.Separate directories for each environment with environment-specific .tfvars files
            b.Common modules directory shared across environments
        
            terraform/
            ├── modules/
            │   ├── networking/
            │   ├── compute/
            │   └── database/
            ├── dev/
            │   ├── main.tf
            │   └── dev.tfvars
            ├── staging/
            │   ├── main.tf
            │   └── staging.tfvars
            └── prod/
                ├── main.tf
                └── prod.tfvars

        -Workspace Approach:
            a.Single codebase with different workspaces for each environment
            b.Environment-specific configuration controlled by variables
            c.Works well for simpler setups but can be limiting for significantly different environments
        
        -Repository Approach:
            a.Separate repositories for shared modules and each environment
            b.Environment repos import modules from the shared modules repo
            c.Useful for organizations with strict access control requirements
